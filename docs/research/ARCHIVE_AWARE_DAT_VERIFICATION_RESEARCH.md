## 1. Current architecture audit

### 1.1 The DAT audit pipeline today

- `crates/archivefs-core/src/dat/sources/audit_run.rs` — `run_dat_audit` (audit_run.rs:269-483) is the orchestrator: parses DAT file(s) → builds a `DatIndex` → walks a folder (`scan_local_files`, audit_run.rs:649-732) → hashes every file found (audit_run.rs:396-436) → calls `crate::dat::audit::audit_files` (audit_run.rs:443) → optionally annotates with rename policy. **CONCLUSION FROM SOURCE**: audit_run.rs:1-40 module doc states explicitly this is the only place that produces evidence for `audit_files`; no other scanner exists in the codebase (confirmed by `rg` across `dat/`).
- The walker is bounded: `MAX_SCAN_DEPTH = 8` (audit_run.rs:67), `MAX_SCAN_FILES = 25_000` (audit_run.rs:75), `MAX_SCAN_ENTRIES_EXAMINED = 200_000` (audit_run.rs:78). It descends breadth-first via an explicit queue (audit_run.rs:673-728), never recurses, sorts children for determinism (audit_run.rs:716), and **does not follow symlinked directories** (audit_run.rs:641-648 doc comment) but does collect symlinked files and defers the follow decision to the read policy.
- Hashing per file goes through `crate::identity_source::hashing::hash_file_reporting` (audit_run.rs:411, imported at audit_run.rs:59), which is chunked (`HASH_CHUNK_BYTES = 256 * 1024`, hashing.rs:45) and cancellable (checked inside the read loop — I confirmed the loop structure in hashing.rs:288-330; cancellation is checked before the file starts, audit_run.rs:397-399, and `hash_file_reporting`'s own doc, hashing.rs:19-22, states the flag is checked every chunk).
- Every read (both the walker's `read_dir`/`symlink_metadata` and the hasher's file open) is read-only; `hash_file_reporting` opens through `crate::safe_read::open_bounded_read` (hashing.rs:314, imported hashing.rs:29) which enforces `TrustedRoots` (see §1.4). audit_run.rs's own module doc (audit_run.rs:10-17) states this is the only filesystem-mutating surface check: there is none — `read_dir`, `symlink_metadata`, and `hash_file_reporting` are the *entire* filesystem surface.
- Comparison logic lives in `crates/archivefs-core/src/dat/audit.rs`: `audit_files` (audit.rs:179-198) calls `audit_one` (audit.rs:200-297) per file, which tries SHA-256 → SHA-1 → MD5 → CRC32+size → filename, in that order (audit.rs:19-26 doc, confirmed by the loop at audit.rs:207-225). `AuditVerdict` (audit.rs:35-69) is the exhaustive result enum; see §8 for its full inventory.
- `crates/archivefs-core/src/dat/index.rs` — `DatIndex` (index.rs:29-35) is five `HashMap<String, Vec<DatRomRef>>`s keyed by crc32/md5/sha1/sha256/filename, built once from a `ParsedDat` (index.rs:39-“build”). Collisions are kept, never resolved silently (index.rs:5-7 doc) — this is the same "never guess" precedent `game_identity.rs`'s ambiguous-XEX code follows (§1.3).

### 1.2 `inspector.rs`: exactly how far it already gets you

`crates/archivefs-core/src/inspector.rs` is real and directly reusable, but it is strictly metadata-only today:

- `inspect_archive_with_limit` (inspector.rs:292-355) opens the ZIP via `ZipArchive::new` (parses the central directory once, inspector.rs:301-308) and iterates every entry with **`archive.by_index_raw(index)`** (inspector.rs:323-328). The comment at inspector.rs:319-322 is explicit: *"`by_index_raw` reads this entry's metadata without preparing a decompressor for it — the only reason this module never needs to support (or reject for being unsupported) any particular compression codec: it never decodes entry data at all."*
- **CONCLUSION FROM SOURCE**: inspector.rs currently reads zero bytes of any entry's payload. `InspectorEntry` (inspector.rs:169-185) carries only `name`, `kind`, `uncompressed_size`, `compressed_size`, `compression_method`, `classification` — no hash field exists, no `crc32` field exists (the ZIP central directory's own CRC32 is available via the `zip` crate's `ZipFile`/raw-entry API but is not currently surfaced by this module).
- `INSPECTOR_ENTRY_LIMIT = 100_000` (inspector.rs:24) is the documented safety cap against unbounded memory from a hostile/huge ZIP; `InspectorReport.truncated` (inspector.rs:196) and `total_entries_in_archive` (inspector.rs:200) make truncation explicit rather than silent.
- `classify_entry` (inspector.rs:132-153) and `InspectorEntryClassification` (inspector.rs:46-59) are pure, filename-extension-only, deliberately conservative (inspector.rs:35-39 doc: "never a claim of definitive game/ROM detection"). `is_known_disc_companion` (inspector.rs:159-165) recognizes `.cue`/`.m3u` specifically as companions, not content.
- `InspectorError` (inspector.rs:209-231) already models `ArchiveMissing`, `UnsupportedFormat`, `Encrypted`, `Malformed{path,detail}`, `Io{path,detail}` — encryption is rejected outright *before* any entry is added to the report (inspector.rs:219-223, confirmed by the `raw.encrypted()` check at inspector.rs:329-331 which aborts the whole listing, not just that entry).
- `is_inspectable` (inspector.rs:271-273) is ZIP-only today (inspector.rs:6-8 doc explicitly reserves 7z/RAR for the same module later, "not a parallel one").

**Verdict**: `inspector.rs` gives you archive opening, central-directory enumeration, bounds, and classification for free. It gives you **nothing** for payload hashing — that is genuinely new work, but it belongs *inside this module* (adding a payload-reading function alongside `inspect_archive`), not a parallel scanner.

### 1.3 `game_identity.rs`: the precedent that matters most

`crates/archivefs-core/src/game_identity.rs` already solves — and ships tests proving it solves — the two hardest problems this feature needs: (a) reading payload bytes out of a ZIP member safely and boundedly, and (b) failing closed on ambiguity instead of guessing.

- `inspect_zip_iso` (game_identity.rs:781-891) and `inspect_zip_xex` (game_identity.rs:918-1000+) both: open the outer ZIP through `open_read_only_regular`/`TrustedRoots` (game_identity.rs:784, 921); reject if `archive.len() > MAX_ARCHIVE_MEMBERS` (`MAX_ARCHIVE_MEMBERS = 4_096`, game_identity.rs:18) before touching any entry (game_identity.rs:802-810, 939-947); iterate with `by_index_raw` exactly like `inspector.rs` and reject on `raw.encrypted()` (game_identity.rs:821-828, 958-965); filter candidate members by extension; and then apply the **exact ambiguity rule** this brief needs generalized:
  ```
  if iso_members.len() != 1 {
      add_unavailable(report, IdentityStatus::Ambiguous, "ZIP contains multiple ISO members; none was selected implicitly");
      return;
  }
  ```
  (game_identity.rs:841-848; the XEX sibling is at game_identity.rs:978-985, identical shape.)
- This is pinned by real, passing tests: `zip_with_one_xex_reads_only_the_xex_header` (game_identity.rs:3577-3598) asserts exactly one member is read and `bytes_read <= XEX_HEADER_PREFIX_BYTES`; `zip_with_multiple_xex_members_is_ambiguous_not_guessed` (game_identity.rs:3601-3622) builds a ZIP with two `.xex`-named members and asserts the verified title id is `None` and an `IdentityStatus::Ambiguous` evidence item exists. **CONCLUSION FROM SOURCE**: "ambiguous → fail closed, never guess" is not a proposal in this codebase, it is already shipped and regression-tested for archive members. The new archive-DAT-verification feature should reuse this exact shape (one plausible match → proceed; zero → a specific "not found" state; more than one → a specific "ambiguous" state, never an implicit pick).
- Payload reads are bounded by member size and a hard cap: `member_size.min(MAX_BYTES_READ)` for most platforms, or a much smaller header-only cap for GameCube/Wii (`DOLPHIN_HEADER_BYTES`, game_identity.rs:865-874); `MAX_BYTES_READ = 64 * 1024 * 1024` (game_identity.rs:17). Reads use `entry.by_ref().take(read_cap).read_to_end(&mut data)` (game_identity.rs:876) — i.e. the *decompressing* `by_index` entry (not raw), read incrementally into a capped buffer, never the whole member unconditionally.
- `MAX_NESTED_CONTAINER_DEPTH = 1` (game_identity.rs:26) is the existing, already-enforced precedent that this codebase does not currently support nested containers beyond one level (ZIP→ISO or ZIP→XEX, not ZIP→ZIP→anything). Directly informs §2's nested-ZIP question.
- `hash_bounded_file` (game_identity.rs:700-722) is a size-bounded SHA-256 helper (1 MiB buffer, checked-add overflow guard, hard `maximum` cutoff) used for **loose** (non-archived) ROM hashing (`MAX_LOOSE_ROM_BYTES = 64 * 1024 * 1024`, game_identity.rs:28). `oversized_loose_rom_fails_closed_without_hashing` (game_identity.rs:3431-3444) proves a file one byte over the limit is never hashed at all (`bytes_read == 0`, verdict `ResourceLimitReached`) rather than partially hashed. This is the fail-closed-on-size precedent that a member-size limit for archive verification should mirror.
- `StableFileMetadata` (game_identity.rs:724-748: `len`, `modified`, and on Unix `dev`+`inode`) is a second, independent precedent for "identity for cache-invalidation purposes," alongside `FileFingerprint` in `hashing.rs` (§1.4, §10) — both use size+mtime(+inode on Unix), never path alone.

### 1.4 `safe_read`: composition, not a parallel policy

`crates/archivefs-core/src/safe_read/mod.rs` (module doc: safe_read/mod.rs:1-51) is the single read-only, symlink-aware file-open policy for the whole build. `TrustedRoots` (safe_read/mod.rs:64) and `open_bounded_read` (safe_read/mod.rs:269) govern **opening the outer file only** — path validation, symlink policy, `O_NOFOLLOW|O_CLOEXEC`, device/inode re-check (safe_read/mod.rs:17-49). It has no concept of "inside an archive" and does not need one: once the outer `.zip` is opened through `open_bounded_read`/`open_read_only_regular` (as `game_identity.rs` already does at game_identity.rs:784, 921), the returned `File`/`SafeFile` is handed to `zip::ZipArchive`, and everything the `zip` crate then does is in-process decompression of already-safely-opened bytes — no further filesystem policy decision is needed for archive-internal reads (a ZIP member is not a path on disk; it has no symlink, no separate open() call, no separate trust boundary). **CONCLUSION FROM SOURCE**: this is exactly how `game_identity.rs` already composes them (open outer file via `TrustedRoots` → hand to `ZipArchive::new` → read a member), so no `safe_read` variant is needed for archive-internal reads. It *would* need extension only if a future format's outer container is not directly `File`-backed (not applicable to ZIP).

### 1.5 Rename planning's current shape

`crates/archivefs-core/src/dat/rename_plan/model.rs` — `RenameProposal` (model.rs:171-219) assumes a single flat `source_path: PathBuf` (model.rs:175) that is both "the thing that was matched" and "the thing that would be renamed." Critically, `ProposalState::Unsupported`'s own doc comment *already anticipates this exact problem*:

> "A canonical name cannot be used safely (**the DAT entry names an internal archive member whose extension differs**, or the source is a symlink)." (model.rs:69-71)

**CONCLUSION FROM SOURCE**: the rename-plan authors were already aware an archive-member DAT match is a real case, and the *current* handling for it is: treat as `Unsupported`, i.e. never propose a rename in that situation today. See §9 for what would need to change.

### 1.6 No second scanner is needed — and one genuinely-new function is

Every walking/bounding/cancellation/progress mechanism archive-aware verification needs already exists in `audit_run.rs`, and every archive-opening/bounded-payload-read/ambiguity-handling mechanism it needs already exists in `game_identity.rs`'s ZIP code and `inspector.rs`. The one genuinely new primitive is: **a function that, given an already-open `ZipArchive` and a chosen member index, hashes that member's decompressed bytes in bounded chunks and returns CRC32/MD5/SHA1/SHA256** — i.e. `game_identity.rs`'s `hash_bounded_file` (game_identity.rs:700-722) generalized from "a whole `File`" to "one `ZipFile` read from a `ZipArchive`," and extended from SHA-256-only to the four algorithms `DatIndex`/`audit_one` actually compare against (CRC32/MD5/SHA1/SHA256, per audit.rs:207-232 and hashing.rs's `LocalHashes`). This belongs in `inspector.rs` (per its own module doc, inspector.rs:6-8) as a new function alongside `inspect_archive`, not as a new module.

## 2. Archive support (ZIP, P0)

- **Streaming vs. extraction — DOCUMENTED FACT (docs.rs, `zip` 8.6.0) + CONCLUSION FROM SOURCE**: `ZipArchive<R>` requires `R: Read + Seek` to open (needed to locate and parse the central directory, which sits at the end of the file). Once open, `by_index`/`by_name` return a `ZipFile` that implements `Read` and decompresses **incrementally as read() is called** — it is not required to materialize the whole member in memory or on disk first. `game_identity.rs`'s own `inspect_zip_iso`/`inspect_zip_xex` already do exactly this: `entry.by_ref().take(read_cap).read_to_end(&mut data)` (game_identity.rs:876) reads a *bounded* number of bytes through the streaming decompressor, never the whole file unconditionally. **Conclusion**: for both Stored and Deflate (the only two methods this build enables — see below), true chunked streaming decompression of a single member is available without ever writing to a temp file or fully buffering the member. Extraction to a temp file is **not** required for P0 ZIP hashing.
- **When extraction is unavoidable — INFERENCE**: only for a compression method the `zip` crate's enabled feature set can't decode at all (P0 enables only `deflate`, per Cargo.toml:66 below), or for a format where a crate doesn't expose a streaming `Read` (7z, out of scope for P0 — see §7/§12 Phase E). For ZIP specifically in P0, no case requires extraction.
- **Cargo.toml feature set — CONCLUSION FROM SOURCE**: `crates/archivefs-core/Cargo.toml:66`: `zip = { version = "8.6", default-features = false, features = ["deflate"] }` for the production build. The `aes-crypto` feature appears only at `Cargo.toml:76`, under `[dev-dependencies]` (used to *build* an encrypted test fixture, per inspector.rs's `write_encrypted_test_zip`, inspector.rs:429-440), **not** in the production dependency. **Conclusion**: encrypted-ZIP *reading* is not available in the shipped binary today — only in test code. P0 should keep `inspector.rs`'s existing behavior: `InspectorError::Encrypted` refuses the whole archive outright (inspector.rs:219-223, 329-331), and archive-DAT-verification must do the same rather than silently skipping just the encrypted member.
- **Compression methods enabled — CONCLUSION FROM SOURCE**: only `deflate` (Cargo.toml:66) plus Stored (built into the crate's core, no feature needed — confirmed by `inspector.rs`'s test fixtures using `CompressionMethod::Stored` with no extra feature, inspector.rs:374-375, 421). `bzip2`, `deflate64`, `lzma-rust2` (LZMA/7z-style), `ppmd-rust`, `zstd` are NOT enabled. A member using one of these must be a **named, distinct refusal** ("unsupported compression method"), never silently skipped or partially hashed.
- **CRC32 as a pre-filter, not a verdict — INFERENCE, grounded in `audit.rs`'s own stated hierarchy**: `audit.rs`'s module doc is explicit that CRC32-based verdicts are deliberately weaker (`ProbableMultipleCandidates` doc, audit.rs:50-55: *"CRC32 is a 32-bit checksum, and several entries sharing one is as likely to be a collision as a real set of identical dumps"*) and `AuditVerdict::is_confident()` (audit.rs:89-94) explicitly excludes every CRC32-only verdict. The ZIP central directory's stored CRC32 is metadata written by whatever tool created the archive — it is *not* independently verified against the decompressed bytes unless something actually decompresses and recomputes it. **Design implication**: a ZIP member's stored CRC32 is safe to use only as a *fast negative pre-filter* — "if the stored CRC32 doesn't even appear in the DAT index, skip the expensive cryptographic hash for this member" — never as the basis for an `Exact`-tier verdict on its own, exactly mirroring how the existing `audit_one` already treats loose-file CRC32 (Probable/ProbableMultipleCandidates, never Exact). The real risk of trusting a *stored* CRC32 without recomputing it against decompressed output: a corrupted or maliciously crafted central-directory record could claim a CRC32 that doesn't match the actual bytes, and a `Probable`-tier result derived from it should still say "based on stored archive metadata, not verified against decompressed content" in its provenance (§8) if the crypto hash step is ever skipped for performance — P0 should not skip it; the crypto hash should always be computed for any member reaching an `Exact`-tier verdict.
- **Multiple files in one archive**: handled entirely by member-selection (§3); not a separate safety concern.
- **Nested archives (ZIP-in-ZIP)**: **should be explicitly refused in P0**, not attempted. `game_identity.rs`'s `MAX_NESTED_CONTAINER_DEPTH = 1` (game_identity.rs:26) is the existing, enforced precedent — this codebase does not currently open a container found inside another container. `inspector.rs`'s `InspectorEntryClassification::NestedArchive` (inspector.rs:56, includes `.zip`/`.7z`/`.rar`/`.tar`/`.gz`/`.bz2`/`.xz` per `NESTED_ARCHIVE_EXTENSIONS`, inspector.rs:100) already *labels* such members without opening them — the DAT-verification design should do the same: a nested archive is a named, listed, unopened member; if it's the *only* plausible content candidate, the result is a specific "unsupported: nested archive not opened" state, not silent skip and not a crash.
- **Malformed archives**: `inspector.rs`'s `InspectorError::Malformed{path,detail}` (inspector.rs:224-227) and `game_identity.rs`'s `IdentityStatus::Invalid` on `ZipArchive::new` failure (game_identity.rs:791-800) are the existing pattern — a central-directory parse failure must produce a specific `CorruptArchive`-class result (§8), never a partial report.
- **Encrypted archives**: refuse the archive outright at the inspection/candidate-discovery step, per §2.3 above — treat as unsupported, not browse-only-but-verify-anyway. (Browsing without decrypting, per `InspectorError::Encrypted`'s current behavior, already refuses even to *list* an encrypted archive's entries — so DAT verification can never even reach member selection for one.)
- **Archive bombs / decompression-ratio protection — genuinely new, not yet present anywhere in this codebase (CONCLUSION FROM SOURCE, confirmed by grep — no "ratio" or "bomb" term appears in `inspector.rs`, `game_identity.rs`, or `dat/`)**: P0 must add this. Design: since the ZIP central directory already reports both `compressed_size` and `uncompressed_size` per entry *before* any decompression happens (inspector.rs:343-345 — this data is free, already surfaced by `by_index_raw`), a ratio check (`uncompressed_size / compressed_size` above a fixed ceiling, e.g. the classic 1000:1-ish "zip bomb" heuristic used by many archive scanners — **UNCERTAIN on the exact ceiling value**, needs a product decision, not a format fact) plus an absolute `uncompressed_size` cap can both be enforced *before* a single byte is decompressed, exactly mirroring how `MAX_ARCHIVE_MEMBERS` (game_identity.rs:18) and `MAX_BYTES_READ` (game_identity.rs:17) are already checked before touching entry data.
- **Huge members**: same mechanism as above — a per-member `uncompressed_size` cap, checked against central-directory metadata before decompression begins, refusal is a named state (not a generic error).
- **Duplicate member names within one archive**: the `zip` crate permits duplicate names in the central directory (this is a known real-world malformation some archivers produce); `by_name` returns only one entry. **INFERENCE**: candidate discovery must therefore iterate `by_index_raw` **by index**, not `by_name`, exactly as `inspector.rs` and `game_identity.rs` already do (inspector.rs:314, game_identity.rs:812, 949) — this sidesteps the duplicate-name ambiguity entirely, and if two *indices* share a name, both become separate candidates for the ambiguity check in §3.
- **zip-slip / path traversal inside archive entries — DOCUMENTED FACT (docs.rs) + CONCLUSION FROM SOURCE**: the `zip` crate exposes `ZipFile::enclosed_name`, documented as the sanitizing accessor used by the crate's own `extract` path. **Neither `inspector.rs` nor `game_identity.rs` currently calls `enclosed_name`** — both use `raw.name()` (inspector.rs:333) or `raw.name_raw()` (game_identity.rs:829-830) directly, because neither module ever turns an entry name into a filesystem path (inspector.rs never extracts; `game_identity.rs` only reads entry *bytes* into memory, never writes them out). **This remains true and sufficient for archive-DAT-verification**: since the P0 design never extracts a member to disk (streaming-only, per above), zip-slip is a non-issue for verification itself — it becomes relevant only if/when a later phase writes extracted bytes anywhere, which P0 does not do. If a member's stored name is later shown to a user or used to *derive* a proposed rename basename, ordinary path-safety normalization (already present in `rename_plan`, not audited in depth here per the task's scope) applies, not archive-specific handling.
- **Unsupported compression methods**: a specific, named `UnsupportedArchive`-class result (§8) per member, not skipped silently — see the compression-methods point above.

**"Fail safely" summary for §2**: every case above resolves to one of a small set of *named* non-exact outcomes (`AmbiguousArchive`, `UnsupportedArchive`, `CorruptArchive`, `NeedsReview` — §8) — never a partial hash treated as if it were complete, and never a guess presented as a match.

## 3. Member selection

Principle (grounded directly in the already-shipped precedent, game_identity.rs:841-848 / 978-985, §1.3): **exactly one plausible candidate → proceed; zero → a specific not-found state; more than one → a specific ambiguous state, never an implicit pick.** The hard part for DAT verification, as the brief notes, is that "plausible" can't only mean "matches a well-known extension" the way XEX/ISO detection does — a `.bin`, `.rom`, or extensionless member is common in real ROM sets. The design below is DAT-metadata-driven disambiguation, layered *in order of strength*, exactly mirroring `audit_one`'s own strongest-evidence-first structure (audit.rs:200-225):

1. **DAT-provided exact identity first.** For every non-directory, non-companion member (`is_known_disc_companion`, inspector.rs:159-165, excludes `.cue`/`.m3u`; `classify_entry`'s `Documentation`/`Artwork` buckets, inspector.rs:142-146, exclude NFO/README/box-art the same way `audit_run.rs` never treats them as ROM evidence), compute the member's cryptographic hash (§2) and look it up in the existing `DatIndex` (index.rs:29-35) exactly as `audit_one` does for loose files. A member whose hash matches exactly one DAT ROM entry is unambiguous *by construction* — no filename/size heuristic is even needed. This is the strongest, and should be tried first, per member.
2. **If no member's raw hash matches anything**, apply normalization (§5) to remaining plausible candidates (`LikelyContent`-classified members, inspector.rs:53, plus any member with a ROM-like extension whether or not it's in the fixed `LIKELY_CONTENT_EXTENSIONS` list) and repeat step 1 against the normalized bytes.
3. **If more than one member reaches a hash match** (raw or normalized) against the *same* DAT entry or against *different* DAT entries, the archive is `AmbiguousArchive` (§8) — never picked by size, position, or filename plausibility. This mirrors `zip_with_multiple_xex_members_is_ambiguous_not_guessed` exactly (game_identity.rs:3601-3622), generalized from "multiple `.xex` files" to "multiple members that hash-match something."
4. **If exactly one plausible-content member exists and zero DAT candidates match it** (raw or normalized), that member is `NotInCatalogue` — still a specific member-level result, not archive-level ambiguity.
5. **Companion files (README/NFO/artwork) alongside one ROM**: recognized and ignored using the existing classification, not counted as ambiguity contributors — `classify_entry`'s `Documentation`/`Artwork` buckets (inspector.rs:142-153) plus `is_known_disc_companion` (inspector.rs:159-165) for `.cue`/`.m3u` already answer "is this a companion, not independent content" for the disc-image case; extending the same *pattern* (not necessarily the same fixed list) to NES/cartridge-style companions (`.nfo`, `.txt`, `.md`, `.sfv`, `.sha1`, `.md5` — already in `DOCUMENTATION_EXTENSIONS`, inspector.rs:96-97) requires no new logic, only reuse.
6. **Multi-disc archives, BIOS bundles, merged sets (base ROM + clones/parents in one archive)**: these are cases where *more than one member legitimately corresponds to *more than one* DAT entry*, each independently verifiable — this is different from ambiguity (§3.3, one member matching many candidates or many members matching the same candidate). **Design**: when every member independently DAT-hash-matches a *distinct* DAT ROM entry (no overlap), the archive should produce **one verified result per member**, not a single archive-level verdict — i.e. `ExactFromArchiveMember` is scoped to (archive, member) pairs, not to the archive as a whole. This falls naturally out of doing member selection *before* choosing a "the" candidate: there is no single-candidate assumption baked in if the result model is per-member from the start.
7. **Nested directories inside a ZIP**: no special handling needed — `zip::ZipFile::name()` already returns the full internal path including any `folder/` prefix (confirmed by `inspector.rs`'s `directories_and_files_are_distinguished` test, inspector.rs:546-571, which finds `folder/inner.txt` by its full stored name); member selection operates on the flat list of (name, index) pairs regardless of nesting depth inside the archive's own namespace — this is unrelated to *nested archives* (§2), which is the ZIP-inside-ZIP case, refused separately.

**Never heuristic, always deterministic**: nothing above ever ranks candidates by filename similarity, "looks like the biggest file," or position in the archive — every disambiguation step is either a DAT-hash match (exact, cryptographic) or a structural classification already proven safe elsewhere in this codebase (companion-file recognition). This is the same discipline `audit_one` already applies to loose files (strongest hash wins, CRC32 is downgraded, filename alone is the weakest and clearly labeled `FilenameOnly`).

## 4. Performance / limits

The existing `audit_run.rs` bounds (`MAX_SCAN_FILES = 25_000`, audit_run.rs:75; `MAX_SCAN_DEPTH = 8`, audit_run.rs:67; `MAX_SCAN_ENTRIES_EXAMINED = 200_000`, audit_run.rs:78) already establish that a single audit run can enumerate tens of thousands of top-level files. Each of those files can now, additionally, be an archive containing multiple members, so the design must bound the *product*, not just the outer count:

- **Bounded concurrency**: not currently present in `audit_run.rs` (its walk-then-hash loop, audit_run.rs:396-436, is sequential — **CONCLUSION FROM SOURCE**, no `thread`/`rayon`/`spawn` appears in that file). **INFERENCE**: P0 should keep the same sequential-per-outer-file model for consistency and to avoid introducing new concurrency-safety surface into a just-hardened module; if concurrency is added later, it should bound *outer files in flight*, not spawn unbounded per-member work, and should reuse whatever concurrency primitive (if any) a future non-archive change introduces rather than inventing an archive-specific one.
- **Streaming hashing**: extend `hash_bounded_file`'s pattern (game_identity.rs:700-722 — fixed buffer, chunked read loop, checked-add overflow guard) to read from a `ZipFile` (a `Read` impl) instead of a `File`, computing CRC32+MD5+SHA1+SHA256 in the same pass, mirroring `hash_file_reporting`'s existing four-algorithm loop (hashing.rs:288-330 — confirmed it already computes CRC32/MD5/SHA1 together in one chunked pass; SHA256 is computed separately elsewhere in the codebase, e.g. `hash_bounded_file`, so the archive-member version should compute whichever set the DAT verification path needs, likely all four to match `audit_one`'s full algorithm ladder, audit.rs:207-232).
- **Member-size limits**: per-member `uncompressed_size` cap read from central-directory metadata *before* decompression (§2), analogous to `MAX_BYTES_READ` (game_identity.rs:17) and `MAX_LOOSE_ROM_BYTES` (game_identity.rs:28) — exact cap value is a product decision (**UNCERTAIN**), not a format fact; the *mechanism* (check declared size before reading, refuse without reading if over) is the existing, proven pattern (`oversized_loose_rom_fails_closed_without_hashing`, game_identity.rs:3431-3444).
- **Archive-count limits**: none needed beyond the existing `MAX_SCAN_FILES` (an archive is just one more "file" the outer walk already counts) — but the walk's per-file work now potentially includes opening a ZIP and iterating its central directory, so the existing `MAX_SCAN_FILES` ceiling (25,000) combined with `INSPECTOR_ENTRY_LIMIT`/`MAX_ARCHIVE_MEMBERS` (100,000 / 4,096 respectively, inspector.rs:24, game_identity.rs:18 — these two numbers currently *disagree*, worth reconciling in implementation, not a research blocker) already bounds total member-level work per run.
- **Decompression-ratio protection**: see §2 — must be added, does not exist today.
- **Cancellation**: `audit_run.rs`'s pattern is "checked before every file, and (per `hash_file_reporting`'s doc) inside every chunk" (audit_run.rs:26-28 doc; hashing.rs:19-22 doc). **CONCLUSION FROM SOURCE, extends cleanly**: the same `&AtomicBool` reference already threaded through `run_dat_audit` → `hash_file_reporting` can be threaded one level deeper into an archive-member hashing loop with zero new cancellation infrastructure — check it once per member (before opening) and once per chunk (inside the read loop), exactly like the existing per-file/per-chunk checks.
- **Progress reporting**: `DatAuditProgress::Hashing{index,total,file_name}` (audit_run.rs:130-135) already reports per *outer* file, explicitly *not* per-chunk ("a per-chunk callback over 25,000 files is a great deal of traffic for a number nobody reads," audit_run.rs:408-410). **INFERENCE**: per-member-within-archive progress should follow the same philosophy — report per member (a new, sibling progress variant, e.g. "hashing member N of M inside file X"), not per chunk within a member, to avoid the same traffic problem one level down.
- **Cache strategy**: see §10.
- **Reuse of archive CRC32 metadata**: see §2 — pre-filter only, never a verdict basis alone.
- **Avoiding filling `/tmp` or the root filesystem**: because P0's ZIP member hashing is streaming (§2 — `ZipFile: Read`, chunked into a hasher, never written to disk), there is no code path in this design that writes an extracted ROM anywhere. **This must remain an explicit invariant**, stated the same way `inspector.rs`'s own test proves it for listing (`inspection_performs_no_filesystem_writes`, inspector.rs:712-747, asserts byte-for-byte archive and directory-listing equality before/after) — a corresponding test for the new hashing path (assert no new files exist under any temp directory after hashing thousands of archive members) should be part of the P0 test plan (§11).

## 5. NES header normalization

### 5.1 The format, from nesdev.org (fetched live for this report)

**DOCUMENTED FACT** (nesdev.org, "INES" page): the 16-byte iNES header layout is:
- Bytes 0-3: magic `$4E $45 $53 $1A` ("NES" + MS-DOS EOF byte).
- Byte 4: PRG-ROM size, in 16 KiB units.
- Byte 5: CHR-ROM size, in 8 KiB units (0 = CHR-RAM).
- Byte 6 (Flags 6): bit0 nametable arrangement, bit1 battery-backed PRG-RAM, **bit2 trainer presence**, bit3 alternative nametable layout, bits4-7 mapper number low nibble.
- Byte 7 (Flags 7): bits0-1 VS/PlayChoice flags, **bits2-3 NES 2.0 identifier** (value `10` binary / decimal 2 in that 2-bit field = NES 2.0; anything else is iNES 1.0 or an archaic variant), bits4-7 mapper number high nibble.
- Bytes 8-15: meaning depends on format version (iNES 1.0 vs NES 2.0), full breakdown below.
- **Trainer location, DOCUMENTED FACT**: when Flags 6 bit2 is set, a 512-byte trainer block appears **immediately after the 16-byte header and before PRG-ROM data**.

**DOCUMENTED FACT** (nesdev.org, "NES 2.0" page), bytes 7-15 in NES 2.0 mode specifically:
- Byte 7 bits2-3 = binary `10` (bit2 clear, bit3 set) identifies NES 2.0 — "chosen so that it does not collide with any valid iNES header."
- Byte 8: upper nibble = submapper number; lower nibble = mapper number bits 8-11 (extending byte 6's mapper nibble).
- Byte 9: lower nibble = PRG-ROM size upper 4 bits (extends byte 4); upper nibble = CHR-ROM size upper 4 bits (extends byte 5).
- Byte 10: lower nibble = volatile PRG-RAM shift count; upper nibble = non-volatile PRG-NVRAM/EEPROM shift count. Actual size = `64 << shift_count` bytes when nonzero.
- Byte 11: same shift-count scheme as byte 10, for CHR-RAM/CHR-NVRAM.
- Byte 12: lower 2 bits = CPU/PPU timing (0 = NTSC RP2C02, 1 = licensed PAL RP2C07, 2 = multi-region, 3 = Dendy/UA6538).
- Byte 13: meaning depends on byte 7 bits0-1 (Vs. System vs. extended console type).
- Byte 14: lower 2 bits = count of "miscellaneous ROM" chips present.
- Byte 15: default expansion device (peripheral expected at `$4016`/`$4017`); value `$01` = standard NES/Famicom controllers.

### 5.2 Decoding the verified vector byte-by-byte

Given header `4E 45 53 1A 08 10 40 08 00 00 00 00 00 00 00 01`:

| Byte | Value | Field | Meaning |
|---|---|---|---|
| 0-3 | `4E 45 53 1A` | Magic | `"NES"` + `0x1A` — valid iNES/NES2.0 magic |
| 4 | `0x08` | PRG-ROM size | 8 × 16 KiB = 131,072 bytes |
| 5 | `0x10` | CHR-ROM size | 16 × 8 KiB = 131,072 bytes |
| 6 | `0x40` = `0100 0000` | Flags 6 | bit2 (trainer) = **0 → no trainer**; mapper low nibble = `0x4` |
| 7 | `0x08` = `0000 1000` | Flags 7 | bits2-3 = `10` binary → **NES 2.0**; mapper high nibble = `0x0` |
| 8 | `0x00` | Submapper/mapper ext | submapper 0; mapper bits8-11 = 0 |
| 9 | `0x00` | PRG/CHR size MSB | no extension beyond bytes 4/5 |
| 10 | `0x00` | PRG-RAM/NVRAM | shift count 0 → no PRG-RAM declared |
| 11 | `0x00` | CHR-RAM/NVRAM | shift count 0 → no CHR-RAM declared |
| 12 | `0x00` | CPU/PPU timing | NTSC (RP2C02) |
| 13 | `0x00` | System type | standard |
| 14 | `0x00` | Misc ROM count | 0 |
| 15 | `0x01` | Default expansion device | standard NES/Famicom controllers |

- **Mapper number** = (byte7 & 0xF0) | (byte6 >> 4) | (byte8 low nibble << 8) = `0x00 | 0x04 | 0` = **4 (MMC3)**.
- **Internal consistency check**: PRG (131,072) + CHR (131,072) = **262,144 bytes**, exactly equal to the given unheadered payload size (262,144 bytes) and to `262,160 − 16` for the headered file. Trainer bit is clear, and no trainer-sized (512-byte) gap exists between header-implied size and payload size — fully consistent with a header that describes exactly this payload with no trainer. **CONCLUSION**: the vector's header bytes are internally consistent with a real NES 2.0 header for a 128 KiB PRG + 128 KiB CHR, mapper-4, NTSC, no-trainer, standard-controller cartridge — nothing in the byte layout looks fabricated or malformed.
- Byte 15 (expansion device) and bytes 8/10-14 are **pure metadata** that do not affect what bytes get hashed (see §6.2) — they describe the emulated hardware, not the payload's byte content.

### 5.4 Fail-closed normalization rule (design, not implementation)

Exactly as scoped in the task:

1. **Raw hash exact-match is always tried first**, unchanged — this is nothing new, it's step 1 of §3's member-selection ladder (and, for a *loose* NES file outside an archive, it's exactly what `audit_one` already does today, audit.rs:207-225). Normalization is only even considered after a raw match fails.
2. **Only under confirmed NES-family context.** "Confirmed" should mean **both** signals agree, not either alone: (a) the DAT entry itself carries NES/Famicom-family platform metadata (the DAT's own `platform`/system field — **INFERENCE**: `crates/archivefs-core/src/dat/model.rs`/classification metadata was not deeply re-audited for this report per the task's scope, but `audit_run.rs`'s `DatAuditRequest.platform` field, audit_run.rs:96-99, shows platform *is* already threaded through the audit request as a first-class, provenance-carrying value — reusing that field to gate "is this an NES-family audit" is the natural fit), **and** (b) the local file's extension is `.nes` or `.unh`/unheadered-convention or similar (a second, independent, cheap check). Requiring both avoids normalizing a file that merely happens to sit in an NES-named folder but is a different platform's ROM misfiled there, and avoids normalizing based on extension alone when the DAT itself is not NES/Famicom.
3. **Only a DAT-provided header, never invented.** The 16 bytes prepended in-memory must come from the *matching DAT entry's own header field* if the DAT format carries one, or more likely (since most DAT ecosystems, e.g. No-Intro, publish the *headered* hash as the canonical entry and separately may publish a "headerless"/"unheadered" companion hash for the same game) from **trying the specific, finite set of header byte-strings that this DAT entry's own published metadata implies is correct for it** — never a general lookup table keyed by mapper number guessed from filename, and never a heuristic "most common header for this game's approximate era." **UNCERTAIN**: the exact mechanism by which "the DAT-provided header" is obtained depends on details of the specific DAT format/ecosystem parsers (`crates/archivefs-core/src/dat/parsers/`) that were out of this report's scope to fully audit — this needs a follow-up pass specifically on whether any currently-parsed DAT format (Logiqx/ClrMamePro/etc., per audit.rs's test fixture using `DatFormat::Logiqx`, audit.rs:363) carries an explicit header field, or whether the only safe source of "the DAT-provided header" is the *headered variant's own full hash*, used as a target to test against rather than a header to literally copy.
4. **Virtual prepend/remove only, in memory, never touching the source file.** Read the archive member (or loose file) fully into a bounded buffer (§2/§4 size limits already apply), construct a new byte sequence with the candidate header prepended (or, symmetrically, with a detected header stripped, for the reverse direction — a headered dump needs to match a headerless DAT entry), hash *that* virtual sequence, and compare.
5. **Accept only on an exact resulting hash match against the DAT.** No partial-credit, no closest-match, no "probably this header." If the normalized hash doesn't exactly match any DAT entry, the result is `NotInCatalogue` for that candidate, not a downgraded "probable" verdict — CRC32-style "probable" tiers exist for weak-evidence *loose-file* matches (§audit.rs), but a normalization *guess* that fails to reach an exact hash is not evidence at all, it's a rejected hypothesis, and should not surface as a lesser-confidence match.
6. **Never succeeds silently/probabilistically.** Every acceptance is a byte-exact cryptographic hash match on the *reconstructed* sequence — there is no fuzzy scoring anywhere in this rule.

## 6. Trainers / nontrivial NES cases

- **512-byte trainers — DOCUMENTED FACT**: sit between the 16-byte header and PRG-ROM (§5.1). **Design implication**: normalization must be trainer-aware as a *third* dimension alongside "header present/absent" — the candidate byte sequences to test are not just "raw" and "raw + DAT header," but potentially "raw", "raw + header (no trainer)", and (rarer) "raw with trainer removed + header", depending on what the *raw as-found* bytes actually are. Since trainers are themselves rare in modern DAT-catalogued dumps (most No-Intro-style DATs describe trainer-less dumps), **INFERENCE**: P0 should only attempt trainer-aware normalization when the DAT entry's own declared size positively implies a trainer-sized (512-byte) discrepancy versus the raw file — never assume a trainer is present or absent without that arithmetic check.
- **NES 2.0 extended fields (submapper, PRG-RAM/EEPROM size, console type, timing) — do they affect hash-relevant bytes?** No. **CONCLUSION from §5.2's decode**: bytes 8, 10-15 in the verified vector are all metadata *about* the cartridge/hardware (submapper, RAM sizes, timing region, expansion device) — none of them describe additional payload bytes to include or exclude from the hash. Only bytes 4-5 (and byte 9's extension of them, for very large ROMs) determine how many PRG/CHR bytes exist, and only Flags 6 bit2 (trainer) determines whether a 512-byte block sits in the stream. Every other NES 2.0 byte is metadata a normalizer must faithfully *copy* into the virtual header (since the DAT-provided header is used verbatim, per §5.4 rule 3) but never needs to *reason about* when deciding what payload bytes to hash.
- **Malformed headers (declared PRG/CHR size inconsistent with actual payload length)**: since normalization only ever uses a **DAT-provided** header (§5.4 rule 3) — never one read from an untrusted local file — this case mostly doesn't arise for the header *being applied*. It can still arise if a candidate *raw* file already carries its own (possibly malformed) header that needs stripping before a headerless-DAT-entry comparison: the design should verify byte4/5-implied size against actual remaining payload length before trusting a "strip existing header" transform, and refuse (not guess) on mismatch.
- **Overdumps/underdumps (extra/missing trailing bytes)**: any such file will simply fail every exact-hash comparison, raw or normalized — this is correctly and automatically handled by the "accept only on exact match" rule (§5.4.5); no special-case logic is needed, it falls out of the design for free.
- **Multiple candidate DAT entries sharing the same underlying body** (a game published as both a headered and headerless DAT entry, or under two header variants): this is exactly the "more than one candidate reachable" case. **Design, per the task's explicit requirement**: if normalization (trying the DAT-implied header(s) for more than one plausible DAT entry) produces exact matches against **more than one** distinct DAT entry, the result must be `AmbiguousNormalization` (§8), *never* `Exact`/`ExactAfterNormalization` — even though each individual match is itself a byte-exact cryptographic hash agreement. Ambiguity here is about *which cataloged identity the file represents*, not about hash confidence — the hash confidence is perfect in both branches, but the *identity* is undetermined, which is precisely the state `Ambiguous`-family verdicts exist to represent elsewhere in this codebase (audit.rs:63-64, `AuditVerdict::Ambiguous{detail}` — "candidate exists, but evidence conflicts").

## 7. Other platform normalization (survey only)

| Platform / case | Transform type | Safety/complexity verdict |
|---|---|---|
| SNES copier headers (512-byte header some dumps carry) | **Fixed-size prepend/strip**, same shape as NES | Same confidence tier as NES header normalization is *plausible* — a fixed-size, position-anchored block, same "DAT-provided, exact-match-only" rule should generalize directly. **INFERENCE**, not independently verified against an authoritative SNES-header source in this pass (out of scope per the brief's "survey only" instruction) — mark as UNCERTAIN pending a dedicated nesdev-equivalent source check for SNES copier-header conventions before implementation. |
| Genesis/SMD interleaving (odd/even byte de-interleave) | **Byte-reordering transform**, not a prepend/strip | Materially riskier — this rewrites the *relationship* between every byte pair in the file, not just adds/removes a fixed prefix. A bug here silently scrambles the entire payload rather than failing an exact-match check in an obviously visible way. **Should not be attempted at the same confidence tier as NES header normalization even later** — it needs its own, more carefully reviewed design pass (e.g. proving the transform is self-inverse-verifiable, or requiring bit-for-bit round-trip tests against known-interleaved/de-interleaved DAT pairs) before it earns the "exact-match-or-nothing, DAT-confirmed" trust level. |
| N64 byte-order variants (z64 big-endian / v64 byte-swapped / n64 little-endian) | **Byte-reordering transform** (word/byte swap, not size-changing) | Same risk category as Genesis interleaving — a systematic byte-order transform, not a prepend/strip. Lower complexity than Genesis interleaving (a fixed, well-known swap pattern rather than variable odd/even splitting) but still not a "same confidence tier as NES" case — recommend it as the *first* candidate for a "phase 2 byte-reordering normalizer" specifically because the transform is simpler and better-known than Genesis's, but still gate it behind its own dedicated safety review, not bundle it into the NES-style P0 work. |
| Atari copier headers | **Fixed-size prepend/strip**, NES-like in shape | Plausible same-tier candidate, same caveat as SNES: not independently verified against an authoritative source in this pass — mark UNCERTAIN. |
| Disk metadata wrappers (various platform-specific disk-image container metadata) | Varies by platform/container; not researched in depth here | UNCERTAIN — genuinely out of scope for this survey; flag for a dedicated pass per-platform. |
| Cue/bin multi-file representation | **Multi-file reconstruction**, not a single-file transform at all | Fundamentally different risk class from every case above: verifying a cue/bin disc requires reasoning about *multiple files together* (the .cue sheet's declared track offsets against one or more .bin files), not transforming the bytes of one file. This is architecturally a different feature (multi-file identity, already partially precedented by `inspector.rs`'s `is_known_disc_companion` explicitly *declining* to attempt BIN/CUE pairing today, inspector.rs:155-158 doc: "This deliberately does not attempt BIN/CUE pairing"). Should remain explicitly out of scope, not attempted even at a lower confidence tier, until a separate design addresses multi-file identity as its own problem. |

**Ranking, safest → riskiest, for future extension**: (1) SNES/Atari-style fixed-size copier headers — same tier as NES, pending format-source verification; (2) N64 byte-order swap — byte-reordering but simple/well-known; (3) Genesis/SMD interleaving — byte-reordering, more complex splitting logic; (4) cue/bin multi-file reconstruction — different problem class entirely, out of scope for any near-term "normalization" work.

## 8. Result/provenance model

### 8.1 Proposed result-state enum vs. existing `AuditVerdict`

`AuditVerdict` (audit.rs:35-69) today has exactly 8 variants: `Exact`, `ExactMultipleCandidates`, `Probable`, `ProbableMultipleCandidates`, `FilenameOnly`, `Ambiguous`, `NotInDat`, `NoUsableEvidence`. All 8 describe a **loose file** compared directly against the index; none of them has any concept of "inside an archive" or "after normalization."

The task's proposed archive/normalization-aware states — `Exact`, `ExactFromArchiveMember`, `ExactAfterNormalization`, `AmbiguousArchive`, `AmbiguousNormalization`, `UnsupportedArchive`, `CorruptArchive`, `NotInCatalogue`, `NeedsReview` — is a **different axis** from `AuditVerdict`: `AuditVerdict` answers "how strong is the hash evidence" (crypto hash vs. CRC32 vs. filename), while the new states answer "where did the bytes that were hashed come from, and were they transformed first." **CONCLUSION**: this is a clean *additive* extension, not a restructuring, **provided it is modeled as a second, orthogonal dimension rather than folded into `AuditVerdict` itself** — concretely:

- Keep `AuditVerdict` exactly as-is for the "how strong is the hash match" axis (it already has `Exact`/`ExactMultipleCandidates`/etc. — reused unchanged for whatever hash ultimately gets compared, raw or normalized, member or loose).
- Add a new, separate enum — something like `MatchProvenance` — carrying the "where from / what transform" axis: `LooseFile` (today's only case, implicit), `ArchiveMember{archive_path, member_name, member_index}`, `NormalizedArchiveMember{..., normalization: NormalizationApplied}`, `NormalizedLooseFile{normalization: NormalizationApplied}`.
- Model `AmbiguousArchive`/`AmbiguousNormalization`/`UnsupportedArchive`/`CorruptArchive` as **pre-hash-comparison refusal states** that never reach `AuditVerdict` at all — i.e. they're not verdicts about hash strength, they're reasons no hash comparison could even be attempted or trusted, analogous to how `HashRefusal` (hashing.rs:60-79: `NotReadable`/`TooLarge`/`ChangedWhileReading`/`ReadFailed`/`Cancelled`) already sits *before* `AuditVerdict` in the pipeline for loose files (a refused hash produces `unhashed`+`FilenameOnly`-at-best, per audit_run.rs:421-434, never a fabricated verdict). Archive/normalization refusals should sit in the exact same pipeline position: before the verdict, feeding a "why no full comparison happened" record analogous to `UnhashedFile` (audit_run.rs:104-110).
- `NotInCatalogue` is just `AuditVerdict::NotInDat` reached via an `ArchiveMember`/`NormalizedArchiveMember` provenance — no new verdict variant needed, only the provenance tag.
- `NeedsReview` is the umbrella state `AmbiguousArchive`/`AmbiguousNormalization`/`UnsupportedArchive`/`CorruptArchive` all funnel into for display purposes — a GUI-level rollup, not necessarily a distinct core-level enum variant (the core should keep the specific reason; only presentation needs to say "needs review" as a category).

**Net conclusion for §8.1**: additive, two-axis extension. `AuditVerdict` (hash-strength axis) is untouched; a new provenance type (source-and-transform axis) is added alongside it, and refusal states (archive-level or normalization-level) are modeled as a *pre-verdict* refusal record, mirroring `HashRefusal`'s existing position in the pipeline rather than becoming new `AuditVerdict` variants.

### 8.2 Provenance fields a result must carry

- **Outer path**: the archive's (or loose file's) path on disk — already what `KnownFileEvidence.filepath`/`AuditEntry.local_path` carry today (audit.rs:131, 100).
- **Archive member path** (when applicable): the ZIP-stored entry name (inspector.rs's `InspectorEntry.name`, inspector.rs:179) plus its index (for duplicate-name disambiguation, §2).
- **Raw hashes**: of the bytes exactly as stored/decompressed, unmodified — CRC32/MD5/SHA1/SHA256, same shape as `KnownFileEvidence` (audit.rs:130-138) / `LocalHashes` (hashing.rs, referenced but not the focus of this citation).
- **Normalized hashes** (only present when normalization was attempted): the hash of the *virtual* reconstructed sequence — kept as a **separate** field from the raw hash, never overwriting it, so provenance can always show both "what was actually on disk" and "what it became after normalization."
- **Normalization applied**: an exact, structured description — not a free-text guess — e.g. `{ kind: "iNES/NES2.0 header prepend", bytes: 16, source: "DAT-provided (entry X)" }`, mirroring how `rename_plan`'s `sanitisation_notes: Vec<String>` (model.rs:214-215) already records "what, if anything, was replaced... in deterministic order" for a different kind of transformation.
- **DAT entry matched**: game name + ROM name + algorithm, exactly the fields `AuditVerdict::Exact` already carries (audit.rs:37-41).
- **DAT-provided transformation evidence**: *which* DAT field supplied the header bytes used (per §5.4 rule 3's still-open question about the exact DAT-format mechanism) — this field exists specifically so a reviewer can audit *why* the normalizer trusted a particular header, not just that it did.
- **No-source-modification guarantee**: an explicit invariant/field (even if it's just a always-true marker in the result type, or better, a property proven by unit test rather than a runtime field) stating the archive/file bytes on disk were never written to — mirroring `inspector.rs`'s own `inspection_performs_no_filesystem_writes` test (inspector.rs:712-747) as the pattern to replicate for the new hashing path (§4's cache/perf section already calls for this test).

## 9. Rename/organisation implications

- **Confirmed by `rename_plan/model.rs`'s own doc comment**: `ProposalState::Unsupported` (model.rs:69-71) already explicitly names "the DAT entry names an internal archive member whose extension differs" as a reason a proposal is `Unsupported` *today*. **CONCLUSION FROM SOURCE**: this means the current rename-plan code, when it encounters this situation at all (which — per §1 — it currently cannot, since nothing yet produces an archive-member DAT match to feed it), is already designed to refuse rather than propose something unsafe. The new work does not need to *invent* safe behavior here; it needs to *supply* the archive-member match data that lets this existing `Unsupported` path (or a newly-`Suggested`-eligible path, once the safety case is made — see below) actually get exercised.
- **Using the task's own example** (`Power Blade (USA).zip` containing `Power Blade (USA).unh`, normalized to match a headered DAT entry `Power Blade (USA).nes`): the archive-level rename semantics should be —
  - **The outer archive is what gets renamed, never the member inside it.** `RenameProposal.source_path` (model.rs:175) should continue to mean "the path on disk a future apply stage would rename" — for an archive-member match, that is the `.zip`'s own path, unchanged in kind from today. The proposed basename comes from the matched DAT *game* entry (e.g. rename `Power Blade (USA).zip` to whatever canonical basename the DAT implies for that game — likely still `Power Blade (USA).zip`, extension preserved, since the *archive's* extension is what must be preserved, not the *member's*).
  - **Member contents are never rewritten.** The `.unh` member inside stays exactly as it is — normalization (§5) is a verification-time, in-memory transform; it never touches archive bytes. This is consistent with §2's blanket "verification is 100% read-only against the archive" requirement.
  - **The archive is never recompressed/rewritten during verification**, full stop — nothing in the P0 design (§2, streaming reads only) opens the ZIP in write mode at any point.
- **What `RenameProposal`'s shape needs, precisely**: `source_path: PathBuf` (model.rs:175) already generalizes correctly (it's the archive's path either way — no change needed there). What's currently *missing* is a way to say "this proposal's match came from inspecting member X inside the archive, via normalization Y" — i.e. exactly the provenance fields designed in §8.2, threaded from the audit result through to the proposal. **CONCLUSION FROM SOURCE**: nothing in `RenameProposal` (model.rs:171-219) currently carries an archive-member identity or a normalization record; both are new, additive fields (not a restructuring — every existing field like `game_name`, `rom_name`, `verdict_label`, `match_confident` continues to mean exactly what it means today, just now potentially populated from an archive-member-and-normalization-derived match instead of only a loose-file match).
- **`ExtensionStatus`** (model.rs:104-112, `Preserved`/`Changed`) should be evaluated against the **archive's own extension**, not the member's — a `.zip` containing a `.nes`-implying DAT match is still extension-`Preserved` at the archive level as long as the proposed basename keeps the `.zip` extension; there is no case where an archive-member match should ever propose changing the *outer* file's extension to the member's format, since that would misrepresent what the outer file actually is (still a ZIP).

## 10. Cache design

- **Existing hash-cache concept in `dat/`/`identity_source/`**: no cache exists specifically for DAT audit hashes (**CONCLUSION FROM SOURCE**, confirmed by grep across `dat/` — nothing keyed on hash+fingerprint for audit results). The closest existing precedent is `crates/archivefs-core/src/identity_source/cache.rs`'s `IdentityCache`/`CACHE_FORMAT_VERSION` (cache.rs:1-40+) — a versioned, atomically-swapped (temp-write → sync → readback-validate → rename) JSON file for RomM-sourced identity data, explicitly *not* a SQLite migration because it's "derived data belonging entirely to one optional source... its natural lifecycle is 'one file, atomically swapped'" (cache.rs:6-15). **This is a strong, directly reusable precedent** for an archive-member-hash cache, which is exactly the same shape of problem (derived, optional, safely-discardable data).
- **`FileFingerprint`** (hashing.rs, `path`+`size_bytes`+`modified_unix_seconds`) and `StableFileMetadata` (game_identity.rs:724-748, adds Unix `dev`+`inode`) are the two existing precedents for "identity for cache-invalidation purposes" — both explicitly documented as *invalidation-only*, never trust-establishing on their own (hashing.rs's `FileFingerprint` doc: "used only to invalidate: a hash is discarded when any of these differs, never trusted merely because they match a record from a different file").
- **Safe cache key design for an archive-member hash**, following those two precedents directly:
  - Outer file identity: **size + mtime (+ inode/device on Unix)**, not path alone — reusing `FileFingerprint`'s exact shape (path is still useful as a lookup key, but never as the sole identity signal, per its own stated contract).
  - Archive member identity: **member name + uncompressed_size + CRC32**, all three already available for free from the central directory via `by_index_raw` (inspector.rs:323-345) with zero decompression cost — any of the three changing (name changes, e.g. a re-zip with different internal paths; size changes; or CRC32 changes, e.g. same name but different content re-added to the archive) must invalidate the cached entry. **Note**: the archive's *own* central-directory metadata is a safer invalidation signal than the outer ZIP's mtime alone, since a ZIP can be rewritten with different member content while somehow preserving the same outer mtime in edge cases (e.g. a tool that preserves timestamps) — including member-level CRC32 in the key closes that gap.
  - The hash itself (raw, and separately the normalized hash + normalization description, per §8.2).
  - **A classifier/normalizer version field**, directly modeled on `CLASSIFIER_VERSION` (`classification.rs:16`: `pub const CLASSIFIER_VERSION: &str = "dat-content-p0-v1";`, doc at classification.rs:14-15: "Bump whenever a rule changes meaning. Plans record this value so a later classifier cannot silently reinterpret an already-reviewed action.") — an analogous `NORMALIZER_VERSION` constant, bumped whenever the normalization *rules* change meaning (e.g. adding a new platform, changing how "confirmed NES-family" is decided), so a cached `ExactAfterNormalization` result from an older rule version is never silently reinterpreted as still valid under new rules.
- **What must never be cached as final**: an `AmbiguousArchive`/`AmbiguousNormalization`/`NeedsReview`-class result must either (a) not be cached at all, or (b) if cached for performance (to avoid re-listing a huge archive's central directory every run), be **trivially invalidated the moment more DAT data becomes available** — concretely, keyed additionally by which DAT source(s)/catalogue version contributed to the ambiguity, so adding a new DAT source or updating an existing one invalidates every cached ambiguous result derived from the old catalogue set, never leaving a stale "still ambiguous" cached answer after the actual ambiguity has been resolved by new data.

## 11. Test vectors

Primary regression vector — the Power Blade case, both directions:

1. **Unheadered raw-hash-mismatch**: hash `Power Blade (USA).unh` (262,144 bytes) directly; assert the raw SHA-256 (`4986c3862a04fcf5b22df58b1182ec2ad636e6083714ac7c069adc1639023ebf`) does **not** match the DAT's expected headered-file hash, and the raw-match step of §5.4 correctly falls through to attempting normalization rather than reporting a false negative-final result.
2. **Header-prepended exact match**: prepend exactly `4E 45 53 1A 08 10 40 08 00 00 00 00 00 00 00 01` (16 bytes) to the same payload in memory; assert the resulting 262,160-byte virtual sequence's hash matches the DAT's headered entry exactly, and the source `.unh` file on disk is provably unmodified (byte-for-byte, before/after) — mirroring `inspection_performs_no_filesystem_writes` (inspector.rs:712-747).

## 12. P0 implementation plan

- **Phase A — archive-member abstraction + ZIP streaming verification.** Extend `inspector.rs` (per its own module doc's explicit invitation, inspector.rs:6-8) with a new function alongside `inspect_archive` that, given a chosen member index, streams and hashes that member's decompressed bytes (CRC32/MD5/SHA1/SHA256) with the same bounds/cancellation discipline as `hash_bounded_file` (game_identity.rs:700-722) and `hash_file_reporting` (hashing.rs:288-330). Wire member candidate discovery into `audit_run.rs`'s per-file loop (audit_run.rs:396-436): when a scanned file is ZIP-shaped (`inspector::is_inspectable`, inspector.rs:271-273), branch into archive-member selection (§3) instead of (or in addition to) whole-file hashing. No new module; extends two existing ones.
- **Phase B — NES virtual header normalization.** A pure, filesystem-free function: given raw payload bytes + a candidate 16-byte header, produce the virtual sequence and its hash; entirely testable in isolation against the Power Blade vector (§11 #1/#2) with no archive, no filesystem, no DAT parsing involved — the purest possible unit under test. Lives as its own small module (e.g. `dat/normalize/nes.rs`), consumed by Phase A's member-selection logic (§3 step 2) and equally usable for a loose (non-archived) unheadered NES file.
- **Phase C — result/provenance UI.** Reference the existing GUI pattern from `crates/archivefs-gui/src/dat_sources_page.rs` — the same collapsed-by-default technical-details pattern already used for content classification display (per this session's PR #29 review context, assumed already understood, referenced by name only per the task's instruction). Surfaces the new provenance fields (§8.2) the same way classification evidence is already surfaced.
- **Phase D — rename/organisation integration.** Per §9's findings: thread archive-member + normalization provenance into `RenameProposal` as new, additive fields; the outer-path-gets-renamed / member-never-touched / archive-never-rewritten invariants require no change to `rename_apply`'s journal/rollback/executor machinery (`crates/archivefs-core/src/dat/rename_apply/{journal,rollback,executor,preflight,noclobber}.rs`) — those modules only ever act on `RenameProposal.source_path`, which continues to mean exactly what it means today.
- **Phase E — explicitly deferred, not started in P0.** 7z/RAR/tar archive support; SNES/Genesis/N64/Atari platform normalizers (§7); cue/bin multi-file identity (§7, different problem class). None of this is needed for, or should block, Phases A-D.

**Explicit statement, per the task's scope**: the transaction/mutation engine (`rename_apply`'s journal, rollback, executor — §1.5, §9) remains **completely unchanged**. This entire feature only produces better-informed *verdicts and proposals* that feed into the existing, already-hardened (PR #28/#29) pipeline; it introduces no new mutation engine, no new way to write to disk, and no new way to apply a rename.

## 14. Bottom-line answers

**A. Is ZIP-aware DAT verification safe to build now?**
Yes. Every prerequisite primitive already exists and is already tested: archive opening and bounded enumeration (`inspector.rs`), bounded payload reads from a ZIP member (`game_identity.rs`'s `inspect_zip_iso`/`inspect_zip_xex`), the fail-closed-on-ambiguity pattern (`zip_with_multiple_xex_members_is_ambiguous_not_guessed`), the bounded/cancellable/read-only walker (`audit_run.rs`), and the hash-vs-catalogue comparison logic (`audit.rs`/`index.rs`). The only genuinely new code is a payload-hashing function inside `inspector.rs` and the member-selection/normalization logic layered on top — both additive, both buildable on proven foundations.

**B. Should members be streamed or extracted, and when, if ever, is extraction actually necessary?**
Streamed. The `zip` crate's `ZipFile: Read` decompresses incrementally as bytes are requested (confirmed via docs.rs for the pinned 8.6.0 version), and `game_identity.rs` already reads bounded amounts of member data this way with no temp file involved. Extraction is not necessary for P0 ZIP (Stored + Deflate, the only two methods this build's `Cargo.toml` feature set enables) under any case surveyed in §2. Extraction would only become relevant for a format/compression method the enabled crate features can't stream-decode at all — out of scope for P0.

**C. Exact P0 archive format(s)?**
ZIP only — matching `inspector.rs`'s own current scope and its own doc comment's stated extension point for 7z/RAR "later... not a parallel one." Within ZIP: Stored and Deflate compression only (the two methods `Cargo.toml:66`'s production feature set enables); every other compression method, and every encrypted archive, is a named refusal, not silently skipped.

**D. Is NES header normalization safe with DAT-provided headers, under the exact-match-only contract described?**
Yes, as designed in §5.4/§6: raw-hash-first, DAT-family-confirmed-context-gated, DAT-provided-header-only (never invented/guessed), virtual/in-memory-only, accept-on-exact-match-only, and — critically per §6's explicit requirement — any normalization path that reaches more than one exact match becomes `AmbiguousNormalization`, never `Exact`. The verified Power Blade vector (§5.2, internally consistent per the byte-by-byte decode, with hash values confirmed at canonical lengths per §5.3) demonstrates the underlying concept works exactly as claimed.

**E. What NES cases must remain ambiguous/unsupported in P0?**
Ambiguous normalization (§6, two DAT entries reachable from the same raw body via different header hypotheses) must always resolve to `AmbiguousNormalization`, never a pick. Malformed-header-inconsistent-with-payload cases should refuse the strip/prepend transform rather than guess at the intended size. Trainer-aware normalization should only be attempted when the DAT-declared size arithmetic positively implies a trainer, not assumed by default.

**F. How should archive-member matches map to rename actions?**
The outer archive's path is what gets renamed (`RenameProposal.source_path` unchanged in meaning); the archive's own extension (not the member's) governs `ExtensionStatus`; member contents and the archive itself are never rewritten during verification or (per the existing, unchanged `rename_apply` pipeline) during a subsequent apply. `RenameProposal` needs new, additive provenance fields (archive-member identity, normalization record) — not a restructuring of its existing shape. This is already consistent with the existing `Unsupported` state's own doc comment, which already names this exact scenario (model.rs:69-71).

**G. What performance safeguards are mandatory, not optional, for P0?**
Per-member size caps checked against central-directory metadata before decompression; decompression-ratio/archive-bomb protection (genuinely new, does not exist anywhere in this codebase today — must be added); reuse of the existing chunked-hashing and per-file/per-chunk cancellation-check pattern extended one level deeper (per-member); progress reporting at the member level, not the chunk level, following `audit_run.rs`'s own stated rationale for why per-chunk-over-thousands-of-files is the wrong granularity; and an explicit, test-proven guarantee that no code path ever writes an extracted member to disk (streaming-only), mirroring `inspector.rs`'s existing no-filesystem-writes test.

**H. Recommended first implementation slice?**
Phase B in isolation, first: the pure, filesystem-free, archive-free NES header virtual-prepend/hash function, tested directly against the Power Blade vector (§11 #1/#2). It has zero dependencies on Phase A, is the smallest possible independently-testable unit, and de-risks the exact-match-only normalization contract (§5.4/§6) before any archive-reading code is written. Phase A's archive-member hashing function (extending `inspector.rs`) is the second slice, testable independently against plain (non-NES) ZIP fixtures using the existing `write_test_zip` test-fixture helper already present in `inspector.rs`'s test module (inspector.rs:398-409) before the two phases are wired together.
