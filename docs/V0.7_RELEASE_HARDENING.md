# v0.7 release hardening audit

This is the historical release-gate record for the earlier untagged
`v0.7.0-alpha` integration
candidate. It does not claim that a release exists and does not authorize a
merge, push, or tag.

## Documentation and wording

The current README, changelog, roadmap, workspace version, and visible
Dolphin/Xenia workflow text were audited. Versioned v0.5 release notes and the
untagged v0.6 development records are retained as historical evidence. Design
ledgers that contain superseded branch or implementation claims are explicitly
labelled historical rather than rewritten as if they were current.

Beginner-facing Dolphin/Xenia headings and terminal states now say what the
user can do: find matching cheats or patches, no matching patches, exact game
version not confirmed, and could not load matching content. Provider, adapter,
candidate, provenance, enum names, hashes, and exact paths remain available
where they are useful, chiefly under Details. Historical CLI/API terminology is
not blindly replaced.

The GUI uses one session platform value across Library, Mount, and the Cheats
chooser. Existing regression tests cover routing, stale focus after platform
changes, duplicate headings, remembered profile choice, visible rows at desktop
and 1024x600, and install/undo state. No safe thin-wrapper page removal was
proven in this audit; larger information-architecture ideas are recorded in
`POST_V0.7_GUI_FOLLOWUPS.md`.

## Database and configuration

Migrations are forward-only and ordered 1 through 5. Schema 5 adds only the
nullable `source_folders.assigned_platform` column. Representative schema-3
(v0.5-era) and schema-4 (v0.6 development) databases are upgraded in temporary
fixtures; archive rows and current manual platform assignments are preserved,
and the new source assignment defaults to `NULL`. Each migration is
transactional. A newer schema is rejected before mutation.

Archive identity remains `(source_folder_id, relative_path)`, so a direct image
and a wrapped archive are distinct, and a rescan upserts instead of duplicating.
Removing a source assignment changes only source evidence; manual per-game
history has higher precedence and is not erased. The schema contains no cheat
catalogue, transaction journal, rollback marker, or backup tables. Those are
separate managed files.

Users need no manual database action when upgrading with the v0.7 binary. A
copy of the database should nevertheless be retained before an alpha upgrade.

Existing scalar `source_folders` configuration migrates in memory to enabled
source records; structured source blocks round-trip. Missing required values and
invalid values return explicit configuration errors rather than resetting the
whole file. New state is additive: source assignments live in SQLite and
remembered emulator profiles live in `emulator_profiles.toml`. Native, Flatpak,
and explicit portable profiles remain distinct and are covered by focused
tests. Unknown future config keys are not silently used as security-sensitive
settings.

## Upgrade and rollback drill

Expected forward path:

1. Stop ArchiveFS and copy `library.sqlite3` and the ArchiveFS managed-state
   directory.
2. Run the new binary. Opening the writable library database applies migrations
   4 and 5 as needed. First launch does not scan, mount, download a catalogue,
   assign a platform, or modify a source image merely because the binary opens.
3. Existing source rows, RetroArch journals/backups, catalogue caches, and
   remembered profile records remain in their existing managed paths.

The v0.6 point was an untagged development baseline, not a published tag. Its
schema-4 shape is nevertheless covered by the upgrade fixture.

In-place application downgrade is **not supported**. Older binaries reject the
schema-5 database as newer than they understand. To roll back the application:

1. Stop ArchiveFS.
2. Keep the v0.7 database and managed state untouched for later recovery.
3. Restore the pre-upgrade database copy to a separate path, then run the older
   binary against that compatible copy.
4. Expect the older binary to ignore separate v0.7 catalogue/profile files it
   does not know about. Do not point it at the migrated schema-5 database.

## Dependencies and licences

`cargo tree --workspace` and `cargo metadata --no-deps` were reviewed. The only
new direct crate since the v0.6 development baseline is `toml 0.8`, used for
bounded Xenia patch-document parsing. It is MIT OR Apache-2.0 and compatible
with this project. It parses data only; ArchiveFS owns all network and
filesystem policy around it. Existing direct crates retain their roles:
`ureq` performs bounded HTTPS, `zip` parses approved ZIP inputs, `rusqlite`
writes the library catalogue, `notify` watches sources, `rfd` opens the native
folder picker, `arboard` handles the clipboard, and `eframe` renders the GUI.
Their resolved licences are permissive (principally MIT/Apache-2.0, with `rfd`
MIT) and compatible. `cargo-audit` was not installed, so no advisory result is
claimed and no tool was installed.

## Privacy

The tracked-content token/private-key scan found no credential-shaped secret.
Loopback/private IPs in network-policy tests, `example.invalid` test email
addresses, and neutral `/home/example`, `/home/user`, or `/golden/home` fixtures
are intentional. The campaign ledger, local QA scripts, and historical audit
records contain the maintainer's local workspace paths by design; these files
are not included in the release archive. The GameCube filenames and mount paths
in platform-recovery documentation are explicit manual-QA fixtures supplied for
this recovery and are also not packaged. Release archive contents must be
scanned again after construction.

The first local artifact drill proved that ordinary Rust release builds embed
the builder's Cargo registry path in panic-location strings and that tar owner
metadata can expose the local account. The release workflow now remaps the
builder home to `/build-home`, normalizes file/directory modes, and writes
numeric root ownership into the tar header. A rebuilt extracted bundle contains
no maintainer home path, live ROM path, credential-shaped string, build cache,
local configuration, or untracked file.

## Packaging result

The workflow-equivalent local bundle is
`archivefs-v0.7.0-alpha-x86_64-linux.tar.gz`, with one same-named root
directory. It contains only both binaries, README, changelog, licence,
installer, and example config. `SHA256SUMS` validates both binaries and the
tarball. Executables are mode 0755; documentation/config are 0644; tar owners
are numeric `0/0`. From a fresh extraction, both
`archivefs-cli --version` and `archivefs-gui --version` print
`0.7.0-alpha` without needing a config, database, network, or display server.
The GUI still requires a desktop display for its normal window.

## Error and recovery evidence

Temporary-fixture tests exercise missing and unreadable sources, a source
removed during scan, malformed ZIP/RVZ/XEX input, unavailable catalogue
network, corrupted cache, read-only destinations, injected write/journal
failure, missing or changed backups, interrupted journals, and stale async
results. The expected terminal contract is a visible success, blocked,
partial-failure, unavailable, or retry state: never panic, false success,
endless loading, silent reset, or source-file mutation. Disk-full behavior is
represented by injected atomic-write failure; a real full filesystem was not
created for this alpha audit.

## Performance smoke

All measurements used generated temporary fixtures on the audit host; they are
approximate, not promises:

- Initial debug-build scan and SQLite persistence of 10,000 empty representative
  archive entries: 3.45 s, about 20.4 MiB peak RSS. An unchanged rescan took
  2.72 s.
- Unknown-only database listing: 0.07 s, about 18.2 MiB peak RSS. Startup plus
  `library-status` against that database: 0.03 s, about 11.1 MiB peak RSS.
- In-process filtering of 10,000 GUI rows across GameCube, Unknown, platform
  switching, and chooser population: 11.4 ms in a debug test build.
- Dolphin catalogue fetch/index fixture: 0.03 s test body; Xenia cached-index
  fixture: 0.02 s test body. Whole filtered Cargo invocations were 0.62 s and
  0.34 s respectively and peaked near 68 MiB, mostly test-harness/build runtime.

The audited hot paths are single passes plus deterministic chooser sorting;
catalogues are loaded on state transitions/background work, not reparsed per
frame. No clear performance regression or accidental quadratic loop was proven,
so no production optimization was added.

## Manual proof still required

The live ROM collection is excluded from automated tests. Before release,
complete the eight-step checklist in `PLATFORM_LIBRARY_RECOVERY.md`, plus launch
both extracted binaries in the real desktop environment and exercise Dolphin
and Xenia install/undo with disposable emulator-profile fixtures.
